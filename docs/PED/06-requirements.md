# Requirements and Acceptance Criteria

> **PED v1.0 section.** Owner: Don.
> Authored here in Markdown and compiled to `docs/PED/exports/PED_v1.0.docx` (DEC-002).
> The compiled document is an output — never edit it directly, and never treat it as the source of truth.

Requirements follow the quality characteristics in ISO/IEC/IEEE 29148 [3]: necessary, unambiguous, singular, feasible, verifiable. Any requirement that could not be given a verification method was rewritten or removed — nine NFRs were rewritten because the drafts used unmeasurable language such as "fast", "user-friendly" and "secure" (AI-002, AI-003). Prioritisation is MoSCoW (DEC-009), with Must reserved for requirements without which the minimum business capabilities [1, §3] are not met; this makes the RSK-12 contingency executable, since scope is reduced in a defined order rather than renegotiated under pressure. NFRs are structured on ISO/IEC 25010 [4]: performance (001, 013), reliability (002, 011), security (003–006, 012, 014), usability (007, 008), maintainability (009), cost (010).

## 6.1 Functional requirements

| ID | Requirement | Source | Pri. | Acceptance criteria | Verification |
|---|---|---|---|---|---|
| FR-001 | An Administrator shall create user accounts and assign exactly one role to each account; self-registered accounts shall default to the Requester role. | SH-05 | Must | Given an Administrator on the user administration screen, when a valid email and role are submitted, then an active account exists with that role and no other role, and the creation is written to the audit trail. | Functional test + audit record inspection |
| FR-002 | The system shall authenticate a user by email address and password before granting access to any function other than sign-in and password reset. | SH-05, SH-09 | Must | Given an unauthenticated visitor, when any application URL other than sign-in or password reset is requested, then access is refused and the visitor is redirected to sign-in with no request data disclosed. | Automated negative-access test |
| FR-003 | The system shall enforce four roles - Requester, Staff, Manager, Administrator - and permit each role only the operations authorised for it. | SH-04, SH-09 | Must | Given an authenticated user in role R, when an operation not authorised for R is attempted, then the operation is refused with an authorisation error and no state change occurs. | Automated role x operation matrix test (NFR-004) |
| FR-004 | The system shall allow a user to reset a forgotten password through a single-use, time-limited link sent to the registered email address. | SH-01 | Should | Given a registered user requesting a reset, when the emailed link is used within its validity period, then a new password may be set; when the same link is reused or used after expiry, then it is refused. | Functional test, positive and negative |
| FR-005 | A Requester shall submit a service request capturing title, description, category and location as mandatory information. | SH-01 | Must | Given an authenticated Requester with all four mandatory fields completed, when the request is submitted, then a request is stored with a unique reference, status New, the submitter recorded and a submission timestamp; and the reference is displayed to the Requester. | Functional test + database inspection |
| FR-006 | The system shall require the Requester to select a category from a controlled list maintained by an Administrator, and shall reject free-text categories. | SH-04 | Must | Given the submission form, when no category is selected, then submission is refused with a field-level message; and the category selector offers only values from the active controlled list. | Functional test + boundary test |
| FR-007 | A Requester shall view the current status of any request they submitted. | SH-01 | Must | Given a Requester with at least one submitted request, when the request is opened, then the current status, the date of the last status change and any resolution note are displayed. | Functional test |
| FR-008 | A Requester shall view a list of all requests they have previously submitted, most recent first. | SH-01 | Must | Given a Requester with n submitted requests, when the request list is opened, then exactly those n requests are listed with reference, category, submission date and status, and no request belonging to another user appears. | Functional test + negative-access test |
| FR-009 | The system shall notify the Requester in-app and by email when their request is accepted, rejected, updated with a comment, or completed. | SH-01 | Must | Given a request owned by Requester X, when its status changes to Accepted, Rejected or Resolved, then an in-app notification and an email are generated to X within 5 minutes, containing the reference, the new status and any reason. | Functional test + notification log |
| FR-010 | An authenticated Requester and authorised Staff shall exchange comments attached to a request record; personal contact details shall not be exposed. | SH-01, SH-02 | Should | Given a request with an assigned staff member, when either party adds a comment, then the comment is stored against the request with author and timestamp and is visible to both, and no email address or telephone number of the other party is displayed. | Functional test + privacy review (NFR-012) |
| FR-011 | A Staff user shall view the service requests they are authorised to see, including unassigned requests and requests assigned to them. | SH-02 | Must | Given a Staff user, when the queue is opened, then unassigned requests and requests assigned to that user are listed, and requests assigned to another staff member are not shown by default. | Functional test |
| FR-012 | A Staff or Manager user shall search by reference or keyword and filter and sort the request list by category, status, assignee, priority and submission date. | SH-02 | Must | Given a list of requests, when a filter or sort is applied, then only matching requests are returned in the requested order, and combining two filters returns the intersection. | Functional test + performance test (NFR-001) |
| FR-013 | An authorised user shall view the complete detail of a request including its full status and assignment history. | SH-02 | Must | Given an authorised user opening a request, when the detail view is displayed, then submitted information, current status, assignee, all comments and the complete ordered change history are shown. | Functional test |
| FR-014 | A Manager shall assign a request to a Staff user, a Staff user shall accept an unassigned request, and a Manager shall reassign an assigned request. | SH-03 | Must | Given an unassigned request, when a Staff user accepts it, then that user becomes the assignee and the assignment is written to the audit trail; and when a Manager reassigns it, the previous and new assignee are both recorded. | Functional test + audit record inspection |
| FR-015 | The system shall permit only defined status transitions across New, Accepted, In Progress, On Hold, Resolved, Closed and Rejected, and shall refuse any undefined transition. | SH-04 | Must | Given a request in status Closed, when any transition other than the defined reopen path is attempted, then it is refused and the status is unchanged; and every permitted transition is recorded with actor and timestamp. | State-transition test covering the full permitted and forbidden matrix |
| FR-016 | An assigned Staff user shall record actions taken and shall record resolution information when moving a request to Resolved. | SH-02 | Must | Given a request being moved to Resolved, when no resolution note is supplied, then the transition is refused; when a note is supplied, the note is stored against the request with author and timestamp. | Functional test, positive and negative |
| FR-017 | An assigned Staff user shall move a request to Resolved, and a Manager shall move a Resolved request to Closed. | SH-02, SH-04 | Must | Given a Resolved request, when a Manager closes it, then the status becomes Closed with actor and timestamp recorded; and a Staff user attempting to close it directly is refused. | Functional test + authorisation test |
| FR-018 | A Staff or Manager user shall reject or return a request to the Requester, and the system shall require a reason. | SH-02 | Should | Given a request being rejected, when no reason is supplied, then the rejection is refused; when a reason is supplied, the request status becomes Rejected, the reason is stored and the Requester is notified (FR-009). | Functional test, positive and negative |
| FR-019 | A Manager shall view counts of open, in progress, overdue, resolved and closed requests for a selected period. | SH-04 | Must | Given a known data set for a period, when the dashboard is opened for that period, then each displayed count equals the count obtained directly from the stored records for that period. | Functional test against a seeded data set |
| FR-020 | A Manager shall view request activity broken down by category, status, assignee and time period. | SH-04 | Must | Given a seeded data set, when a breakdown by category is requested, then every active category is represented and the sum of the category counts equals the total request count for the period. | Functional test with reconciliation check |
| FR-021 | The system shall identify a request as overdue when its elapsed open time exceeds the configured target resolution time for its category. | SH-04 | Must | Given a category with a configured target of T hours and a request open for more than T hours in a non-terminal status, when the dashboard or queue is viewed, then that request is flagged overdue; and a request open for less than T hours is not flagged. | Boundary test at T-1, T and T+1. NOTE: target values are not yet agreed - see RSK-05 and SCOPE-D-02. |
| FR-022 | A Manager shall export the filtered request list to CSV for offline analysis and record keeping. | SH-04 | Should | Given a filtered request list of n rows, when export is selected, then a CSV file is produced containing exactly n data rows with a header row and the same field values as displayed. | Functional test + row-count reconciliation |
| FR-023 | An Administrator shall create, rename and deactivate categories, and shall configure the target resolution time for each category. | SH-05 | Must | Given a category referenced by existing requests, when deactivation is attempted, then the category is deactivated for new submissions while existing requests retain it; and deletion that would orphan a request is refused. | Functional test + referential-integrity test |
| FR-024 | An Administrator shall change a user's role and deactivate a user account. | SH-05 | Must | Given an active user with assigned open requests, when the account is deactivated, then the user can no longer sign in, the assigned requests remain visible to the Manager for reassignment, and the change is written to the audit trail. | Functional test + audit record inspection |
| FR-025 | The system shall record every status change and every assignment change with the acting user, timestamp, previous value and new value, and shall not permit these records to be edited or deleted through the application. | SH-04, SH-09 | Must | Given a request that has undergone k status or assignment changes, when the history is viewed, then exactly k ordered entries are shown each with actor, UTC timestamp, previous value and new value; and no application function exists that edits or deletes an entry. | Functional test + code review + negative test (NFR-006) |
| FR-026 | On submission the system shall warn the Requester when an open request with the same category and location already exists, while still permitting submission. | SH-02 | Could | Given an existing open request with category C and location L, when a Requester submits a new request with category C and location L, then a warning listing the possible duplicate is displayed and the Requester may confirm or cancel. | Functional test |

## 6.2 Non-functional requirements

| ID | Attribute | Requirement | Pri. | Acceptance criteria | Verification |
|---|---|---|---|---|---|
| NFR-001 | Performance - list response | The 95th percentile server response time for a filtered request list of up to 500 records shall not exceed 2.0 seconds with 10 concurrent users on a warm instance. | Must | A load test of 10 concurrent users over 5 minutes against a 500-record data set reports a 95th percentile response time of 2.0 seconds or less. Cold-start latency is measured and reported separately (see NFR-002). | Load test, M3 |
| NFR-002 | Availability | The staging deployment shall be available at least 95% of the time between 07:00 and 18:00 SAST on weekdays across the M3 evaluation period. Cold-start latency of up to 30 seconds after idle is a declared and accepted limitation of the free-tier hosting constraint. | Should | An uptime log across the evaluation period shows availability of 95% or more within the stated window, and the observed cold-start latency is recorded as a known limitation in the PED. | Uptime monitoring log, M3 |
| NFR-003 | Credential storage | Passwords shall be stored only as a salted adaptive hash (bcrypt with cost factor 10 or greater, or Argon2id). No password shall be stored in plaintext or in any reversible form. | Must | Inspection of the stored user records shows no plaintext or reversible password value, and code review confirms the hashing algorithm and cost factor. | Database inspection + code review, M3 |
| NFR-004 | Authorisation enforcement | 100% of role-restricted operations shall reject a request from an unauthorised role with an authorisation error and without any state change. | Must | An automated test matrix covering every role against every restricted operation reports zero unauthorised successes. | Automated role x operation matrix test, M3 |
| NFR-005 | Secrets handling | No password, API key, token, connection string or private key shall be present in the repository or in its commit history. | Must | An automated secret scan on every pull request and a full-history scan both report zero findings. | Automated secret scan, from M1 |
| NFR-006 | Auditability | 100% of status and assignment changes shall be recorded with actor, UTC timestamp, previous value and new value, and shall not be modifiable through the application. | Must | For a scripted sequence of k changes, the audit record contains exactly k entries with all four fields populated, and no application endpoint accepts an update or delete against an audit entry. | Functional test + negative test, M3 |
| NFR-007 | Usability of submission | An untrained Requester shall complete a valid submission within 3 minutes and no more than 3 screens. | Should | In a moderated test with 5 representative participants, at least 4 complete a valid submission unaided within 3 minutes. | Moderated usability test, M3 |
| NFR-008 | Accessibility | Body text shall meet a contrast ratio of at least 4.5:1, every form input shall carry a programmatic label, and the submission flow shall be fully keyboard operable (WCAG 2.1 AA subset). | Should | An automated accessibility check reports zero contrast or missing-label violations on the submission and request-detail screens, and the submission flow is completed using keyboard input only. | Automated accessibility scan + manual keyboard walkthrough, M3 |
| NFR-009 | Maintainability | Automated unit tests shall cover at least 70% of lines in the business/service layer, and static analysis shall report zero critical findings on the main branch. | Should | The pipeline coverage report shows 70% or more line coverage for the business/service layer and the static-analysis stage reports zero critical findings. | CI report, M3 |
| NFR-010 | Cost | Recurring monetary cost shall be R0.00 for the duration of the academic project, and the projected operational cost at 100 active users and 1 000 requests per month shall be documented. | Must | A platform cost review lists every service in use, its free-tier limit, current consumption against that limit, and a costed projection at the stated volume. | Cost review, M2 and M4 |
| NFR-011 | Recoverability | A backup of the request data shall be taken at least daily, a documented restore procedure shall exist, and a restore shall be verified at least once before M4. Recovery point objective 24 hours; recovery time objective 4 hours. | Should | A backup schedule is evidenced, and a restore into a clean environment is performed and timed, producing a data set matching the source at the backup point within the stated RTO. | Documented restore rehearsal, M3/M4 |
| NFR-012 | Privacy of requester information | Requester contact details shall be visible only to the assigned Staff user, the Manager and the Administrator roles. | Must | Negative-access tests confirm that a Requester and an unassigned Staff user cannot retrieve another requester's contact details through any interface, including direct record access. | Automated negative-access test, M3 |
| NFR-013 | Capacity | The system shall hold at least 500 user accounts and 5 000 request records within the selected free-tier storage limits without breaching NFR-001. | Should | With 500 users and 5 000 requests seeded, storage consumption remains inside the documented free-tier limit and the NFR-001 load test still passes. | Capacity test, M3 |
| NFR-014 | Input validation | 100% of user-supplied input shall be validated server-side; rejected input shall return a field-level message without discarding the data already entered. | Must | For each input field, a boundary and an invalid-type case are submitted with client-side validation bypassed; every case is rejected server-side with a field-level message and the retained form values are redisplayed. | Automated boundary and negative test, M3 |

## Appendix B — Request Lifecycle States (compiled PED appendix)

The model underlying FR-015 — a requirements artefact stating which transitions are legitimate, not how they are implemented.

| State | Meaning | May move to | Actor |
|---|---|---|---|
| New | Submitted, not triaged | Accepted, Rejected | Requester creates; Staff/Manager moves on |
| Accepted | Acknowledged as valid work | In Progress, On Hold, Rejected | Staff, Manager |
| In Progress | Assigned and being worked | On Hold, Resolved | Assigned Staff |
| On Hold | Blocked or awaiting information | In Progress, Rejected | Assigned Staff, Manager |
| Resolved | Work complete, resolution recorded | Closed, In Progress (reopen) | Staff resolves; Manager closes or reopens |
| Closed | Terminal — confirmed complete | None | Manager only |
| Rejected | Terminal — reason mandatory | None | Staff or Manager (FR-018) |

Open question carried to M2 (FEC-02): whether Closed may be reopened and by whom. Left open deliberately — a business rule the team cannot authorise without a stakeholder, and guessing would embed an unvalidated rule in the acceptance criteria.

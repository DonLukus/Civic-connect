### 2026-10-18 - Audit trail made append-only in the database (FR-025, NFR-006)
**Who:** Don, with Claude Code assistance (AI-051) - **Type:** persistence, tests
**What:** Added three SQLite triggers on `request_audit`: abort any UPDATE, abort any DELETE, and abort any INSERT that reuses an existing id (`INSERT OR REPLACE` / `REPLACE` delete the old row without firing the DELETE trigger, because SQLite only does that with `PRAGMA recursive_triggers`, off by default). They are in `schema.sql` for new databases and in the `wsgi.py` migration for existing ones. Previously nothing stopped application code or a stray query from rewriting history. No application code ever updated or deleted audit rows, so behaviour is unchanged.
**Evidence:** `tests/test_audit_immutability.py` (10 cases: insert still works, including an explicit new id; update, delete, `INSERT OR REPLACE` and `REPLACE` refused with the original row unchanged when read back through a new connection, with `recursive_triggers` both off and on; an older database gains all three triggers on startup and the replace guard is live). The replace cases fail against the previous two-trigger schema. Full suite and Ruff results are recorded in the PR. RTM execution evidence for TR-007 and TR-008 updated; their statuses are unchanged because the lifecycle beyond acceptance is still unbuilt.
**Review finding:** an independent AI-assisted review (Emile's team) reproduced `INSERT OR REPLACE` rewriting an audit row through the first version; fixed here. No HTTP exploit or human test execution is claimed.
**Limit:** Triggers protect against the application and its connection, not against someone with direct write access to the database file, who could drop them.
**Review:** Needs two non-author approvals.
